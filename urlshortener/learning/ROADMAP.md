# URL Shortener — Spring Boot Learning Project

## 1. Project Purpose

This project is my **first substantial Spring Boot application**.

The primary objective is **learning Spring Boot and backend development**, not simply producing a working URL shortener.

I already have a reasonably strong foundation in Java, so Java fundamentals should not be re-taught unless a Spring concept depends on an important Java mechanism.

The project should be built progressively so that Spring concepts are introduced when the application actually needs them.

The intended learning philosophy is:

```text
Build something
    ↓
Encounter a problem
    ↓
Understand the problem
    ↓
Learn the Spring mechanism that solves it
    ↓
Implement it
    ↓
Test it
    ↓
Reflect/refactor
```

The application should therefore evolve incrementally rather than being generated as a complete architecture from the beginning.

# 4. Project Scope

The first version will be a relatively small URL-shortening backend.

The core functionality is:

```text
Long URL
    ↓
Create short URL
    ↓
Store mapping
    ↓
Return short URL
    ↓
User accesses short URL
    ↓
Lookup mapping
    ↓
HTTP redirect
    ↓
Original URL
```

Example:

```text
Original URL:

https://example.com/some/very/long/url
```

becomes something similar to:

```text
http://localhost:8080/Ui901nvwL
```

which redirects to:

```text
https://example.com/some/very/long/url
```

---

# 5. MVP API

The first version will have two primary endpoints.

## 5.1 Create Short URL

### Endpoint

```http
POST /api/urls
```

### Request

```json
{
  "url": "https://example.com"
}
```

### Successful Response

```json
{
  "shortCode": "Ui901nvwL",
  "shortUrl": "http://localhost:8080/Ui901nvwL",
  "url": "https://example.com"
}
```

The exact response structure can be reconsidered later if there is a good architectural reason.

---

## 5.2 Redirect

### Endpoint

```http
GET /{shortCode}
```

Example:

```http
GET /Ui901nvwL
```

The application should:

1. Look up the short code.
2. Retrieve the original URL.
3. Return an HTTP redirect response.
4. Let the client/browser navigate to the original URL.

The backend should **not** make a GET request to the destination URL merely to perform the redirect.

Conceptually:

```text
Browser
   │
   │ GET /Ui901nvwL
   ↓
URL Shortener
   │
   │ Database lookup
   ↓
https://example.com
   │
   │ HTTP Redirect
   ↓
Browser
   │
   │ GET https://example.com
   ↓
Destination
```

# 6. Data Model — Current Decision

The initial database model is intentionally simple.

Conceptually:

```text
URL_MAPPING

id
link_key
original_url
created_at
```

Example:

```text
id | link_key  | original_url                    | created_at
---|-----------|---------------------------------|-------------------
1  | Ui901nvwL | https://example.com            | ...
2  | X92LmP81a | https://google.com/search      | ...
```

## Fields

### `id`

Internal database identifier.

This does not need to be exposed publicly.

### `link_key`

The public short identifier.

Example:

```text
Ui901nvwL
```

Current decision:

- exactly 9 characters
- generated by the application
- should contain uppercase letters, lowercase letters, and digits
- must be unique

### `original_url`

The destination URL.

Example:

```text
https://example.com
```

### `created_at`

Timestamp indicating when the mapping was created.

# 7. JSON Storage Decision

Do **not** store the original URL as JSON inside a database column.

For example, do NOT create:

```json
{
  "url": "https://example.com"
}
```

inside a database field.

Instead, store the URL directly:

```text
original_url = "https://example.com"
```

The JSON structure belongs at the API boundary, not necessarily inside the database.

For example:

```json
{
  "url": "https://example.com"
}
```

is an HTTP request representation.

The database can simply store:

```text
original_url
```

This decision may be revisited only if a future requirement provides a genuine reason for JSON storage.

# 8. Short Code Generation

The current design is:

```text
Generate random 9-character code
        ↓
Check whether code already exists
        ↓
If collision → generate another
        ↓
Save
```

The character set will initially be:

```text
A-Z
a-z
0-9
```

Therefore there are:

```text
62^9
```

possible combinations.

The application-level collision check is not considered sufficient by itself.

The eventual database design should also enforce uniqueness on `link_key`.

Conceptually:

```text
Application
    ↓
Generate code
    ↓
Check
    ↓
Database UNIQUE constraint
```

This is intentional because the project should teach the difference between:

- application-level validation
- database-level integrity constraints
- race conditions

Do not prematurely over-engineer the ID generation mechanism.

---

# 9. Duplicate Long URLs / Idempotency

If the same long URL is submitted multiple times, the application should **not create multiple mappings** in the MVP.

Example:

First request:

```text
https://example.com
```

creates:

```text
Ui901nvwL → https://example.com
```

A second request for the same URL should return the existing mapping rather than creating another short code.

Conceptually:

```text
POST /api/urls
       ↓
Does original_url already exist?
       │
   ┌───┴───┐
  YES      NO
   │        │
   ↓        ↓
Return    Generate
existing  short code
mapping      ↓
           Save
```

The intended property is:

> Creating a short URL for a given original URL should be idempotent.

This terminology should be preserved and explored during implementation.

---

# 10. URL Validation

An empty or malformed URL should result in:

```text
400 Bad Request
```

However, the application should **not initially perform an HTTP GET against the submitted URL to determine whether it is valid**.

These are different concepts:

```text
URL syntax/validity
        ≠
whether the resource currently exists
```

For example:

```text
https://example.com/missing-page
```

can be a perfectly valid URL even if the destination currently returns:

```text
404 Not Found
```

Therefore the initial implementation should validate the URL itself rather than requiring the destination to respond successfully.

Whether the URL is normalized or whether additional reachability checks are desirable can be explored later.

---

# 11. URL Normalization Decision

The behavior for URLs such as:

```text
https://example.com
```

and:

```text
https://example.com/
```

has **not been implemented as normalization**.

For the MVP, the deliberate decision is:

> Treat URLs exactly as supplied.

Therefore these are currently considered different strings and may produce different short URLs.

Example:

```text
https://example.com
```

and:

```text
https://example.com/
```

are different values for duplicate detection.

This is intentional.

URL normalization can be revisited later as a learning exercise involving URL parsing, canonicalization, and idempotency.

Do not introduce complicated normalization logic during the initial MVP unless specifically requested.

---

# 12. HTTP Behavior

The application should distinguish between backend behavior and frontend presentation.

For example, if:

```http
GET /doesnotexist
```

is requested, the backend should return an appropriate HTTP error such as:

```text
404 Not Found
```

with a useful response body.

The backend should not attempt to provide a frontend loading screen.

A frontend may eventually decide how to display errors or loading states, but the initial project is a backend/API learning project.

---

# 13. POST vs PUT Decision

The MVP will use:

```http
POST /api/urls
```

for creating a shortened URL.

Reason:

The client does not know the generated short-code identifier beforehand.

The server generates:

```text
Ui901nvwL
```

Therefore:

```text
POST /api/urls
```

is the current preferred design.

Do not add PUT simply because both POST and PUT are available.

The distinction between POST and PUT, resource identity, and idempotency should be discussed when relevant.
